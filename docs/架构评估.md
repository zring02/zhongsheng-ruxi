# 架构评估与阶段计划（2026-10-15）

## 一、技术选型结论

沿用 **Node.js + TypeScript 后端、Three.js 前端**，不换 Python/FastAPI。理由：

- 前后端一种语言，动作、事件、观察的类型定义（`src/types.ts`）前后端可以共用，少写一倍胶水代码。
- 这个游戏的后端本质是一个 10Hz 的实时 tick 循环 + 几百个并发的慢 HTTP 调用（大模型），Node 的事件循环天然适合；Python 要上 asyncio 才能做到同样的事。
- 不用 LiteLLM/LangChain：各家模型的"聊天补全"接口只有十几行差异，自己写的适配层（`src/adapters/`）更可控，而且国产模型（DeepSeek、豆包、千问、Kimi、智谱）全部是 OpenAI 兼容接口，一个适配器配不同地址就能接。

## 二、最需要初期攻克的三个难点

### 1. 空间接地：让模型从文字里推出可执行的 3D 动作

这是最大的断层。模型普遍不擅长在文字里做三维相对位置推理，"去挖那块铁矿"在最原始的动作集里要拆成 走过去 → 算出站哪一格 → 转到正确朝向 → 挖，每一步一次调用、每一步都可能算错。

已经做的：感知层把四方向视线、面前三格、附近可见方块（带坐标）、地标方位翻成中文描述，并且这些描述和寻路规则用同一套代码判断，审查时做过全图 9216 个位置的一致性验证。动作失败会以"没做成"写回角色记忆。

接下来要做的：加 `approach`（走到某个方块或某个人跟前并自动面向它）这类以目标为中心的高层动作，把三步调用压成一步；观察里显式给出"上一步结果"和"当前目标"，让模型跨回合不丢上下文。

### 2. 决策节奏、成本与输出可靠性

模型每次决策 2–5 秒，6 个角色每隔几秒各调一次，一小时几千次调用，而且多数是无意义的闲逛。

已经做的：决策是异步的，慢模型不卡别人；每个角色有最短决策间隔；缺 key 自动降级到 mock，所以零成本就能开发和看效果。

接下来要做的（和设计清单线程的"省钱四招"一致）：有事才想（被搭话、有人走近、剧情事件时才调用，平时按日程走）；记忆压缩成摘要；人设固定放提示词开头走各家的前缀缓存；限制输出长度。

### 3. 权威状态：玩家实时输入和 AI 异步决策共存

玩家接入后，输入是每秒多次的实时流，AI 的决策是几秒后才回来的异步结果，两者都要改同一个世界。

已经做的：每个动作执行前都重新校验现场（目标格还在不在、有没有人站着）；角色之间有占位和让路；世界改动统一走 setBlock → 批量下发。

接下来要做的：统一的动作队列，AI 的决策和玩家的输入都投进队列，由 tick 按确定顺序执行，这样交易、偷东西这类需要公平判定的事才站得住。

## 三、阶段一（MVP）：从哪个文件开始

阶段一的目标（tick 循环 + 方块世界 + 几个 AI 走动）已经完成，所以答案是回顾式的：**第一个该写的文件是 `src/voxel.ts`**，也就是世界状态本身。它定义了方块表、网格、"站得住/走得过"的规则和寻路，感知层、动作层、前端渲染全都建立在这份规则上；规则一改，三处都要跟着改，所以它必须最先定下来。

实际的依赖顺序：`types.ts`（共享类型）→ `voxel.ts`（世界）→ `actions.ts`（能做什么）→ `perception.ts`（看到什么）→ `simulation.ts`（循环）→ `server.ts` / `client/`（展示）。

## 四、阶段一已交付的内容

- 48×20×48 的体素世界，带种子的噪声地形，5 个地标区域，树和矿。
- 2 格高角色、1 格台阶、重力、BFS 寻路（目标到不了就走到最近处）、角色之间不重叠。
- 感知层：中文场景描述 + 结构化 JSON。
- 动作：转身、走、寻路、挖、放、说话、表情、发呆；动作注册表自动生成提示词。
- 模型适配层：Claude / OpenAI 兼容（含国产）/ Gemini / Ollama / mock，缺 key 自动降级。
- Three.js 方块渲染（只画露出的面）、小人、名牌、气泡、地标标签、侧边栏日志。
- 经过 5 路代码审查、37 条发现、24 条确认并修复、端到端集成测试通过。

## 五、阶段二、三（v2，2026-10-15 已实现）

- 剧本系统：`scenarios/*.json` 可替换（背景、地标名、方块主题、角色卡、说书人配置、惩罚说法）；`GameSession` 管一局流程，剧情模式限时 60 分钟分 3 个游戏日（每天早上 / 中午 / 傍晚 / 夜里四段），沙盒不限时并自动存档；穿书模式的核心六人按玩家穿成谁动态分配（`coreSets`）。
- 模型分档：`models.json` 的 core / extra / storyteller 三档，国产模型做成预设；提示词限制一到三句，接口 `max_tokens` 卡死。
- 互动动作：approach / whisper / eavesdrop / steal / give / put / take，被发现概率按剧情设计稿的表，惩罚有关押、信任崩塌、谣言传播、失主事后发觉。
- 说书人：真模型（看全局写事件、章回、结局、蝴蝶效应链、感人揭晓）或内置事件池兜底；固定骨架 + 收网大事 + 随机抽 + 玩家中途加剧情；埋好的伏笔由服务器保管，说书人决定何时揭给谁。
- 玩家：与 AI 同一套动作处理器和动作队列，走 WebSocket；玩家视角遮住别人的内心想法、私聊和偷窃。
- 记忆：短期记忆满了压成摘要；对每个人的信任值和具体记得的事；因果日志（AI 说明“因为哪段记忆”）供结算串链。

- 提示词：措辞归“AI 角色提示词”线程（`prompts/` 目录：模板、人设卡、难度、记忆摘要模板），框架只负责拼装（`src/persona.ts` 直接 import 那边的 `render.mjs`）。回合提示词按那边的约定分栏：心情（好感 + 信任）、记忆摘要、别人的原话、听到的、刚发生的、此刻状态、可以说心里话的人、服务器释放的要紧秘密、叫醒原因。模型输出的 `because` 进因果日志，`feel` 改好感。

### 下一步最值得做的

1. 用真实国产模型跑完整一局，调提示词（现在只用 mock 跑通过流程）：看 JSON 稳定性、台词长短、是否被玩家套话。
2. 结算动画（画面线程）：协议里的 `ending.chain` / `ending.reveals` / `epilogues` 就是给它的素材。
3. 多人：现在是单玩家；多玩家需要每条连接绑定自己的角色和视角，动作队列已经按玩家 id 区分，改动集中在 server.ts。
